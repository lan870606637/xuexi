# Day 05 · 异常处理

> 今天要做什么：让你的代码"出问题不死"。
> 测试自动化最常用 —— 一条用例失败不能把后面 999 条都拖崩。

---

## 异常是什么？

程序运行时遇到"出乎意料"的情况，比如：

- `int("abc")` —— 字符串转不了整数
- `open("不存在的文件.txt")` —— 文件没找到
- `data["age"]` —— 字典里没有这个 key
- `10 / 0` —— 除以零

默认行为：**程序立刻崩掉**，后面一行都不执行。

"异常处理"就是用 `try / except` **接住**这个异常，让程序自己决定怎么办（重试？跳过？记日志？）。

---

## 为什么测试场景里特别重要？

举个真实例子：

```
你有 100 条接口测试用例，第 37 条因为网络抖动失败了。
没有异常处理 → 整个测试脚本崩溃，后面 63 条都没跑
有异常处理   → 第 37 条记为 FAIL，第 38 条继续跑
```

再举一个：

```
找页面元素时偶尔超时，但 retry 3 次基本就能找到。
没有异常处理 → 第一次超时就 GG
有异常处理   → 抓住超时异常，再试 2 次
```

## 心法 · 异常处理的 3 个原则

| 原则 | 说明 |
|---|---|
| **只捕获你真的能处理的** | 别滥用 `except Exception: pass`，把所有错误都吞掉，bug 会藏到看不见的角落 |
| **捕获要尽量精确** | 写 `except ValueError`，不要写 `except Exception` 当所有错误来抓 |
| **不知道怎么办就别 try** | 让它崩，崩了你才知道有 bug，比悄悄出错强一万倍 |

---

## 常见踩坑

| 坑 | 后果 | 怎么避免 |
|---|---|---|
| `except: pass` 啥也不做 | bug 永远发现不了 | 至少打个 log |
| 把 try 块写得太大 | 不知道是哪一行抛的 | 缩小到只包"可能出错的那一两行" |
| 用 `except Exception as e` 抓所有 | 连 Ctrl+C 都抓 | 用具体的异常类，必要时用 `except Exception` 但要 `raise` 重抛或记录 |
| 异常被吞了不知道原因 | 排错困难 | 用 `raise ... from e` 保留原始异常 |
